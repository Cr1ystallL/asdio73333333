# Финансовая Безопасность и Инварианты (Financial Security)

Документ описывает математические и архитектурные механизмы защиты платформы от двойных выплат, взломов балансов, гонок параллельных запросов и мошенничества.

---

## 1. Фундаментальные математические инварианты

Финансовое ядро гарантирует соблюдение следующих условий на уровне ограничений СУБД и автоматических проверок:

1. **Инвариант Сохранения Баланса (Conservation of Funds)**:
   В любой момент времени сумма активов на банковских счетах платформы должна быть строго равна сумме обязательств перед пользователями плюс нераспределенная прибыль платформы:
   $$\text{Cash}_{\text{Bank}} = \text{Escrow}_{\text{Campaigns}} + \text{Balances}_{\text{Users}} + \text{Pending}_{\text{Holds}} + \text{RetainedEarnings}_{\text{Platform}}$$
2. **Инвариант Неотрицательности Балансов**:
   Ни один пользовательский лицевой счет или пул кампании не может иметь отрицательное сальдо:
   $$\forall u \in \text{Users}: \text{Balance}(u) \ge 0$$
3. **Инвариант Нулевой Разницы Проводки**:
   $$\sum_{e \in \text{Entries}(T)} \text{Debit}(e) - \sum_{e \in \text{Entries}(T)} \text{Credit}(e) = 0$$

## 2. Защита от Race Conditions (Состояние гонки)

Главный вектор атаки на финансовые сервисы — одновременная отправка двух запросов на вывод одного и того же баланса (Double Spending Attack).

### Архитектурные меры защиты:
1. **Пессимистическая блокировка в транзакции (`SELECT ... FOR UPDATE`)**:
   ```sql
   BEGIN TRANSACTION;
   -- Блокируем строку счета клиппера
   SELECT balance_cents FROM user_accounts 
   WHERE user_id = $1 AND account_code = '2300' 
   FOR UPDATE;
   
   -- Проверяем достаточность средств
   -- Создаем запись в ledger_entries
   COMMIT;
   ```
2. **Распределенный Redis Lock**:
   На уровне API шлюза используется `Redlock` по ключу `lock:payout:user:<user_id>` с TTL = 10 секунд. Второй запрос моментально отсекается с кодом `429 Too Many Requests`.
3. **Idempotency Key (Ключ идемпотентности)**:
   Каждый запрос на пополнение, начисление или вывод обязан содержать уникальный UUID ключ от клиента (`X-Idempotency-Key`). При повторном запросе сервер возвращает закэшированный результат первого запроса.

## 3. Автоматический ночной аудит (Nightly Automated Reconciliation)

Каждую ночь в 03:00 по московскому времени фоновый сервис производит сверку:
- Сопоставляет каждую запись в `ledger_transactions` с выпиской банковского API (Т-Банк Open API).
- Проверяет контрольные суммы всех счетов.
- Если обнаружено расхождение $> 0.00$ ₽:
  - Автоматически выставляется глобальный флаг `SYSTEM_PAYOUTS_FROZEN = true`.
  - Моментально отправляется алерт в защищенный Telegram-канал службы безопасности.
  - Ни одна копейка не покидает платформу до ручного расследования инцидента.
